# 設計

## ゴール／アンチゴール

目的別の親と少数の子、領域別Skillsを分離する。証拠と不明点を引き継ぎ、人の確認時間を減らす。
全ソースをLLMへ投入すること、実装から正式仕様を自動確定すること、無制限の並列化は目標にしない。

## 構造

親3種が共通の子2種を必要時に使用する。初期の子同時数は指示上2、再調査は1巡。
これらはスケジューラによる強制ではない。厳密な上限は利用ホストで設定する。
子は必要なSkillsを読み、根拠付き要約を返す。親は不足と矛盾を統合する。
Spec/sourceリンクは出典・版・構成を持つ。会話履歴だけを証拠台帳にしない。

## フェーズ

1. v0.1: 定義・共通手順・生成・静的検証・模擬評価。製品クライアント受入は利用環境で行う。
2. 同一モデル／同一課題で通常検索、Serena、CodeGraphを比較。合格例と失敗例を蓄積する。
3. 設計支援、製作・検証の専用役割を追加する。差分とテスト、書き込み所有範囲を定める。
4. 固定モデルの実測からモデルルーティングを検討。Fusionとの二重制御を避ける。

## 前提とリスク

- 利用モデルとツールはアカウント／ポリシー次第。設定の存在は動作保証ではない。
- 多数モデルの同意は正しさの証明ではない。
- OSレシピの有効値には対象ビルド環境が必要。解析にもメタデータ実行が伴い得る。
- 子の低価格化を最優先にしない。寿命・並行処理は短い関数でも高難度。
- 保守Agentが評価基準を変更して自分を合格させない。
- シャーロック皇帝の人格は口調と判断姿勢のみ。ホストの権限・安全規則を変更しない。

## やらないこと

社内データの公開、無断のモデル課金、常駐監視、自己増殖、MCP自動インストール、
権限自動緩和、実機への無断アクセス、根拠のない一致率の提示、ベンチマーク正解の改変。
