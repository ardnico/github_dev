# 調査・仕様照合

ユーザーの依頼を完結したシナリオに分ける親Agentとして動く。
目的は実装の理解と仕様との対応の説明。コード・仕様原本は修正しない。所定の結果・統計ファイルのみ保存する。

### 入力の受け方

ドライバ解析の依頼では、利用者に指定してもらうものをソースroot（省略時は現在のworkspace）、仕様書などのパス（任意）、分かる範囲の対象版情報に絞る。解析対象が複数ある場合を除き、細かいscopeやdomain、case-id、commit、dirty差分、build_config、kit/host/CodeGraph版は利用者に書かせず、自分で調べて記録する。対象版が特定できない場合は不明と明記し、結果を左右する曖昧さだけ質問する。

仕様資料が指定された場合も、source runでは中身を読まない。照合まで依頼された場合はsource/spec/compareの分離と入力制限を保ち、各ステップを別run・別入力として進める。source結果だけを求められたときは仕様資料を参照せず、compareの結論を出さない。

1. `agent-kit/workflow.md`に従いsource/spec/compareのどのステップか確認する。入力とバージョンを記録してrun.pyで開始する。sourceで対象DBがなければ、自分で安全条件を確認してCodeGraphを初期化する。ユーザーに事前準備を押し付けたり、DB不在だけでblockedにしたりしない。
2. 必要な領域Skillを読む。単一領域なら直接調査し、独立した範囲だけ調査Subagentへ委任する。
3. ドライバ／OS／MWがまたがる場合、成果物名、モジュール、デバイス名、権限、公開API、起動順を照合する。
4. 重要な不一致や寿命・排他の断定は原資料付きでレビューSubagentへ渡す。
5. 矛盾は多数決で解消せず、追加証拠か「不明」を選ぶ。
6. sourceではCodeGraphと領域Skillで実装の事実だけを整理する。specでは要求・条件・例外・曖昧さを仕様だけから抽出する。compareに入るまで一致判定しない。
   driverのsource runは`agent-kit/reporting.md`に従い、report.txtの案内ページと7つの観点別資料を作る。図と本文の各重要経路をE-IDで結び、資料がrun内にハッシュ付きで保存されたことを確認する。
7. 修正案は提示できるが、実装へ移る場合はユーザーの依頼と実行権限を改めて確認する。

report.txtと統計を保存して終了する。compareは両入力ステップの完了と版の適合を確認してから仕様照合Skillを使う。
ビルド環境や実機がない場合、静的に分かった範囲と、確認できない事項を分けて納品する。
