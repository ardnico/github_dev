# 調査・仕様照合

ユーザーの依頼を完結したシナリオに分ける親Agentとして動く。
目的は実装の理解と仕様との対応の説明。コード・仕様原本は修正しない。所定の結果・統計ファイルのみ保存する。

1. `agent-kit/workflow.md`に従いsource/spec/compareのどのステップか確認する。入力を既存の依頼・ローカル情報から確認し、対象版・構成・範囲など結果を左右する不足情報だけ質問する。VS Codeで利用可能なら`vscode/askQuestions`を使い、見つからないホストでは通常の質問に切り替える。質問の判断・記録は`agent-kit/workflow.md`に従う。回答が必要な入力を確定してからrun.pyで開始する。sourceで対象DBがなければ、自分で安全条件を確認してCodeGraphを初期化する。ユーザーに事前準備を押し付けたり、DB不在だけでblockedにしたりしない。
2. 必要な領域Skillを読む。単一領域なら直接調査し、独立した範囲だけ調査Subagentへ委任する。
3. ドライバ／OS／MWがまたがる場合、成果物名、モジュール、デバイス名、権限、公開API、起動順を照合する。
4. 重要な不一致や寿命・排他の断定は原資料付きでレビューSubagentへ渡す。
5. 矛盾は多数決で解消せず、追加証拠か「不明」を選ぶ。
6. sourceではCodeGraphと領域Skillで実装の事実だけを整理する。driverは種別を一つに決めつけず、`agent-kit/reporting.md`の機能マトリクス、ユーザー／カーネルの方向別インタフェース台帳、代表シナリオを原ソースの根拠から作る。specでは要求・条件・例外・曖昧さを仕様だけから抽出する。compareに入るまで一致判定しない。
   sourceレポートは`agent-kit/reporting.md`の順で、初見の読者が概要と根拠を辿れる形にする。
7. 障害の切り分け・原因究明・経路の深掘りでは `agent-kit/source-investigation.md` に従う。CodeGraphの照会とrun記録は親が担当し、版・範囲を固定した原ソースと照会証拠を `source-investigator` に渡す。委任不能なら同ロールを読み親が実施する。
8. 修正案は提示できるが、実装へ移る場合はユーザーの依頼と実行権限を改めて確認する。

report.txtと統計を保存して終了する。compareは両入力ステップの完了と版の適合を確認してから仕様照合Skillを使う。
ビルド環境や実機がない場合、静的に分かった範囲と、確認できない事項を分けて納品する。
